# ADR-0013：解析前去掉回复外层的格式外壳

- 状态：已采纳
- 日期：2026-11-09

## 背景

ADR-0002 规定输出严格解析，代码块包裹算失败。
2026-11-09 在 A10 上冒烟测试 B0（`zero-shot-score@v2`，20 张）：
提示词已写明“不要代码块”，Qwen3.5-4B 仍然每条都用
` ```json ` 代码块包裹，里面的 JSON 键和分数都对，解析率却是 0。
按旧规则三种提示词可能全部出局，选不出 LoRA 用的提示词；
而这类外壳只是排版习惯，和打分能力无关。
预填回复开头（把 `{` 写进回复）也不能保证格式对，还改变了提示方式。

## 决定

- EVA 双分数的解析（提示词调优、LoRA 评测、检查点选择）
  先去掉以下格式外壳，再按 `EvaDualScoreOutput` 严格解析：
  - 回复开头的一个 `<think>…</think>` 块；
  - 包住整段回复的一个 Markdown 代码块，
    语言标记只能是 `json`、`JSON` 或不写。
- 其余情况照旧算失败：外壳前后有其他文字、多个代码块、
  未闭合的代码块、其他语言标记、多余或缺少的键、超范围、
  残缺 JSON。外壳里的 JSON 一个字都不改。
- `raw_output` 原样保留，事后可以统计多少条带外壳。
- 主仓库 `lora_sft/eval/eva_eval.py` 与 `prompt_tuning/ptune/runner.py`
  用同一个 `unwrap_reply`，由 `test_sync_with_main.py` 核对一致。

## 放弃的方案

- 保持旧规则：基线全部出局，比较失去意义。
- 预填回复开头：不保证格式正确，且 LoRA 评测要跟着改提示方式。
- 宽松提取（在任意文字里找第一个 JSON）：会把说明文字里的
  数字或半截输出当成答案，等于修补。

## 后果

- 提示词调优包需要重新打包上传；提示词文件不变。
- 基线和 LoRA 的解析规则仍然完全相同，提升的算法不变。
- 回复变长：代码块外壳约 29 个 token，`max_new_tokens` 32 仍够用；
  超出会因截断而解析失败，计入失败率。
- 三分数加评语的通用解析器 `parse_prediction` 不在本次范围，
  仍按 ADR-0002 的旧规则。

## 修订（2026-11-09，用户要求解析适应多种格式）

决定第一条和后果第三条改为下面的规则，其余不变：

- 去掉开头的一个 `<think>…</think>` 块后，在回复里找**完整的顶层
  JSON 对象**。恰好一个时，取出这一段原文，按 `EvaDualScoreOutput`
  严格解析；零个或多个时整段照旧解析（必然失败）。
- 因此代码块的样式（三个或两个反引号、`~~~`、任何语言标记、
  未闭合）、行内代码、前后的说明文字都不再导致失败。
- 仍然失败：没有完整对象（截断、只有散落的数字）、两个以上对象
  （分不清哪个是答案）、对象本身不合法（单引号、尾逗号）、
  多余或缺少的键、嵌套在别的键下、超范围。
- 与上面“放弃的方案”里的宽松提取不同：不找数字、不补全、不修改，
  只认 JSON 解析器能完整解析出的唯一一个对象，所以不会把说明文字或
  半截输出当成答案。
- `max_new_tokens` 由 32 提到 64：代码块外壳约 29 个 token，32 只留
  3 个余量，缩进稍多就会截断；解码遇到 `<|im_end|>` 就停，多给的
  上限没有代价。值在训练配置 `selection.max_new_tokens`，调优包、
  LoRA 评测和检查点选择都从这里取。
- 提示词调优包按此重新打包（`prompt-tuning-v1-r3`），旧包的运行结果
  不再使用。
